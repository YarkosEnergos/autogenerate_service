# Сервис генерации

Принимает заказ на генерацию, списывает токены и отдаёт задачу провайдеру. Если провайдер отказал, идёт к следующему по цепочке «ног», а если отказали все — возвращает токены. Каждое движение денег происходит ровно один раз, в том числе при дублях вебхуков, гонках и четырёх процессах.

Стек: Python 3.11+, FastAPI, SQLAlchemy 2 (async, asyncpg), Alembic, PostgreSQL 16, uv.

## Быстрый старт

```bash
docker compose up --build
```

Поднимутся:

| Сервис    | Порт  | Что это                                              |
|-----------|-------|------------------------------------------------------|
| `db`      | 5432  | PostgreSQL                                           |
| `migrate` | —     | одноразовый `alembic upgrade head`, затем завершается |
| `api`     | 8000  | сервис, `uvicorn --workers 4`                        |
| `alpha`   | 9001  | фейковый провайдер alpha                             |
| `beta`    | 9002  | фейковый провайдер beta                              |

Если порты заняты, их можно переопределить: `DB_PORT`, `API_PORT`, `ALPHA_PORT`, `BETA_PORT`.
Swagger: http://localhost:8000/docs.

### Попробовать руками

Вебхуки подписаны: `X-Signature = hex(HMAC-SHA256(сырое тело, WEBHOOK_SECRET))`, по умолчанию секрет `dev-secret`.

```bash
# 1. Пополнить баланс (пользователь создаётся при первой оплате)
BODY='{"payment_id":"p-1","user_id":1,"tokens":100,"status":"succeeded"}'
SIG=$(printf '%s' "$BODY" | openssl dgst -sha256 -hmac dev-secret | awk '{print $NF}')
curl -s localhost:8000/webhooks/payments -H "X-Signature: $SIG" -H 'Content-Type: application/json' -d "$BODY"

# 2. Заказать генерацию
curl -s localhost:8000/generate -H 'Content-Type: application/json' \
  -d '{"user_id":1,"model_slug":"image-fast","prompt":"a cat","ref_images":[]}'
# {"task_id":"..."}

# 3. Посмотреть задачу (статус, текущая нога, история попыток) и баланс
curl -s localhost:8000/tasks/<task_id>
curl -s localhost:8000/users/1/balance
```

Поведение провайдеров меняется на лету, без перезапуска:

```bash
curl -s -X PATCH localhost:9001/behavior -H 'Content-Type: application/json' -d '{"failure_rate":1}'
curl -s -X POST localhost:9001/behavior/reset
```

## API

| Запрос | Что делает |
|---|---|
| `POST /generate` `{user_id, model_slug, prompt, ref_images}` | Списывает цену, создаёт задачу, отправляет на первую подходящую ногу, отвечает `202 {task_id}`. Нет подходящей ноги — `400` (до списания). Не хватает токенов — `402`. Уже 3 активные задачи — `429`. Неизвестная модель или пользователь — `404`. |
| `POST /webhooks/providers/{name}` | Результат от провайдера: `{client_ref, external_id, status: completed\|failed, result_url \| error_type}`. Неверная подпись — `401`, неизвестная попытка — `404`, дубли и поздние вебхуки — `200`. |
| `POST /webhooks/payments` | Оплата `{payment_id, user_id, tokens, status}`. Начисляется только `status=succeeded`, повторы — `200` без начисления. |
| `GET /tasks/{id}` | Статус, `result_url`, текущая нога и история попыток: провайдер, приоритет, статус, тип ошибки, время начала/дедлайн/время окончания. |
| `GET /users/{id}/balance` | Баланс и последние 20 строк журнала. |

## Тесты

Тесты ходят в настоящий Postgres из compose. База `generation_test` пересоздаётся и мигрируется автоматически на старте прогона, рабочую базу `generation` тесты не трогают.

```bash
docker compose up -d db
uv sync
uv run pytest
```

Другую базу можно указать через `TEST_DATABASE_URL`.

Обязательные сценарии из задания:

| Сценарий | Тест |
|---|---|
| 20 одновременных одинаковых вебхуков оплаты дают одно начисление | `tests/test_payments.py::test_twenty_concurrent_identical_payments_credit_once` |
| 10 одновременных failed по задаче на последней ноге дают один возврат | `tests/test_provider_webhooks.py::test_ten_concurrent_failures_on_last_leg_refund_once` |
| Отказ первой ноги: задача завершается на второй, в истории две попытки | `tests/test_provider_webhooks.py::test_first_leg_failure_completes_on_second_leg_with_two_attempts` |
| Поздний completed после срабатывания сторожа | `tests/test_watchdog.py::test_late_completed_is_accepted_while_task_is_still_processing`, `::test_late_completed_after_refund_is_ignored`, `::test_completed_racing_with_watchdog_gives_result_or_refund_never_both` |

После каждого теста фикстура проверяет инвариант `users.balance == SUM(ledger.amount)` для всех пользователей.

Эти тесты запускают приложение в одном процессе через `httpx.ASGITransport`, а провайдеров подменяют `FakeGateway`. Конкуренция при этом настоящая: каждый запрос работает в своём соединении и своей транзакции Postgres, а гарантии держатся именно на БД. Сторож в этих тестах выключен и вызывается явно через `watchdog.run_once()` после сдвига дедлайна в прошлое, поэтому тест правила 6 не ждёт 60 секунд.

### Сквозные тесты против compose

Проверяют то же самое на живом стеке: 4 воркера uvicorn и настоящие фейковые провайдеры.

```bash
PROVIDER_TIMEOUT=5 docker compose up -d --build --wait
uv run pytest -m e2e
```

С `PROVIDER_TIMEOUT=60` (по умолчанию) e2e-тест правила 6 пропускается, чтобы не ждать минуту. Остальные проходят при любом таймауте.

Линтер: `uv run ruff check . && uv run ruff format --check .`

## Миграции

Схема создаётся только миграциями Alembic (`migrations/versions`):

- `0001_initial_schema` — таблицы, ограничения, индексы;
- `0002_seed_catalog` — каталог моделей и ног из задания.

**Как применяются.** В compose это делает отдельный сервис `migrate`: он запускает `alembic upgrade head` и завершается, а `api` стартует только после его успешного завершения (`service_completed_successfully`). Миграции не встроены в старт API, потому что при `--workers 4` их запускали бы четыре процесса одновременно.

Вручную:

```bash
docker compose run --rm migrate              # в контейнере
uv run alembic upgrade head                  # локально, DATABASE_URL из окружения или .env
uv run alembic downgrade -1                  # откатить последнюю
uv run alembic history                       # список ревизий
```

**Как добавить следующую.**

1. Изменить модели в `app/db/models.py`.
2. Сгенерировать черновик: `uv run alembic revision --autogenerate -m "add task tags" --rev-id 0003`.
3. Проверить и поправить файл `migrations/versions/0003_add_task_tags.py`: autogenerate не видит переименования, изменения CHECK и данные. Data-миграции, как `0002`, пишутся вручную (`uv run alembic revision -m "..." --rev-id 0003`).
4. `uv run alembic upgrade head`, затем `uv run alembic check`. Он должен ответить, что расхождений между моделями и схемой нет.

## Архитектура

Слоистая, без лишних абстракций:

```
app/
  api/            HTTP: роуты, pydantic-схемы, проверка подписи, маппинг ошибок в коды
  services/       бизнес-правила и границы транзакций
    tasks.py        создание задачи, переходы между ногами, результат, просрочка
    billing.py      единственное место, где меняется баланс
    payments.py     вебхук оплаты, баланс
    dispatcher.py   отправка попытки провайдеру после коммита
    watchdog.py     сторож просроченных попыток
  repositories/   SQL-запросы, без бизнес-логики
  domain/         enum'ы статусов, доменные ошибки, выбор следующей ноги (чистая функция)
  clients/        HTTP-клиент провайдеров
  db/             модели SQLAlchemy, сессии
  core/           настройки, HMAC
fake_providers/   фейковые alpha и beta (одно приложение, имя из env)
migrations/       Alembic
tests/            интеграционные тесты на реальной БД, e2e против compose
```

Сервис сам открывает транзакцию (`async with session.begin()`), репозитории только выполняют запросы в переданной сессии. Поэтому одна бизнес-операция всегда укладывается в одну транзакцию.

### Данные

- `users(id, balance)`: `balance` — кэш суммы журнала с `CHECK (balance >= 0)`.
- `ledger(user_id, amount, reason, task_id, payment_id)` — журнал: `topup` (+), `charge` (−), `refund` (+).
- `models(slug, price)`, `legs(model_slug, provider, priority, max_ref_images, skip_on_moderation)` — каталог.
- `tasks(status: processing|completed|failed, price, result_url, error, ...)`.
- `attempts(task_id, leg_id, provider, status, external_id, error_type, deadline_at, late_result, ...)` — попытки, это и есть история.

Статусы попытки: `pending` (создана, отправляется) → `sent` (провайдер ответил 202) → `completed` | `failed` | `timed_out` | `cancelled`.

### Жизненный цикл задачи

1. `POST /generate`, одна транзакция: `SELECT user FOR UPDATE` → проверка баланса и лимита активных задач → `INSERT task` → проводка `charge` → `INSERT attempt(pending, deadline_at = now() + PROVIDER_TIMEOUT)` → `COMMIT`.
2. После коммита, в фоне: `POST /tasks` провайдеру с `client_ref = attempt.id` и `callback_url`. Ответ 202 переводит попытку в `sent`. Синхронная ошибка (5xx, 429, таймаут, сеть) считается `technical` и ведёт на следующую ногу, 4xx считается `payload`.
3. Вебхук, ошибка отправки или сторож переводят задачу дальше. Все три пути сходятся в одном методе `TaskService._fail_attempt`:
   - `payload` — задача `failed` и возврат;
   - `moderation` — следующая подходящая нога, кроме ног с `skip_on_moderation`;
   - `technical` или `timeout` — следующая подходящая нога;
   - ноги кончились — задача `failed` и возврат.
4. `completed` — задача `completed`, остальные активные попытки `cancelled`.

Нога подходит, если `max_ref_images >= len(ref_images)`. Выбор следующей ноги — чистая функция `domain/routing.py`, у неё отдельные юнит-тесты.

## Чем обеспечено «ровно один раз»

Защита двухслойная. Первый слой — логика под блокировкой. Второй — уникальные индексы, которые не пропустят дубль, даже если в логике ошибка.

**Любое изменение баланса — это строка журнала.** Баланс меняет только `Billing._post`, и порядок там всегда один:

```sql
INSERT INTO ledger (...) VALUES (...) ON CONFLICT DO NOTHING RETURNING id;
-- только если строка вставилась:
UPDATE users SET balance = balance + :amount WHERE id = :user_id;
```

Оба запроса идут в одной транзакции. Повтор операции упирается в конфликт и баланс не трогает, а операции без строки журнала не бывает.

**Начисление оплаты.** Работает уникальный частичный индекс `uq_ledger_payment_id (payment_id)`. Из 20 одновременных одинаковых вебхуков первый вставляет проводку. Остальные на вставке ждут коммита первого, получают конфликт, ничего не вставляют и не трогают баланс. Не нужны ни `SELECT`-проверки (они дали бы гонку check-then-insert), ни advisory-локи.

**Списание.** Идёт в той же транзакции, что и создание задачи, поэтому задачи без списания и списания без задачи не бывает. Дополнительно стоит уникальный индекс `uq_ledger_task_id_reason (task_id, reason)`: одно `charge` на задачу. Параллельные `/generate` одного пользователя сериализуются через `SELECT ... FOR UPDATE` строки пользователя, поэтому лимит в 3 активные задачи и проверку баланса нельзя обойти гонкой (`test_concurrent_generates_respect_active_limit`).

**Возврат.**
1. Любое событие по задаче (вебхук, синхронная ошибка, сторож) обрабатывается в транзакции под `SELECT ... FOR UPDATE` строки задачи. Попытка перечитывается после получения блокировки, поэтому видны изменения, закоммиченные предыдущим обработчиком (READ COMMITTED).
2. Возврат делается только при переходе задачи `processing → failed`. Из 10 одновременных `failed` первый делает переход и возврат, остальные девять видят неактивную попытку и задачу не в `processing` и отвечают 200, ничего не меняя.
3. Если логика где-то ошибётся, второй возврат не вставит уникальный индекс `(task_id, reason)`.

Попытка задачи в каждый момент одна: это гарантирует уникальный частичный индекс `uq_attempts_task_id_active (task_id) WHERE status IN ('pending','sent')`. Две ноги одной задачи одновременно не работают.

## Сторож и четыре процесса

Состояния в памяти нет: задачи, попытки, дедлайны и журнал лежат в Postgres. Сторож запущен в каждом воркере и раз в `WATCHDOG_INTERVAL` секунд забирает просроченные попытки:

```sql
SELECT tasks.id, attempts.id FROM tasks JOIN attempts ON ...
WHERE tasks.status = 'processing' AND attempts.status IN ('pending','sent') AND attempts.deadline_at <= now()
ORDER BY attempts.deadline_at LIMIT 1
FOR UPDATE OF tasks SKIP LOCKED
```

`SKIP LOCKED` делит работу между сторожами без лидера: задачу, которую держит другой сторож или обработчик вебхука, просто пропускают. Блокируется та же строка задачи, что и в вебхуках, поэтому сторож и вебхук по одной задаче сериализуются. После захвата состояние перепроверяется отдельным запросом. Дедлайн сравнивается с `now()` базы, а не с часами процесса. Тест: `test_concurrent_watchdogs_process_expired_attempt_once`.

Просроченная попытка становится `timed_out` с `error_type=timeout` и дальше идёт по тем же правилам, что и `technical`.

## Что будет при падении процесса посреди обработки вебхука

Всё, что вебхук меняет в БД (статус попытки, статус задачи, возврат, новая попытка следующей ноги), делается одной транзакцией. Поэтому промежуточных состояний нет:

| Где упал | Что будет |
|---|---|
| До `COMMIT` | Postgres откатывает транзакцию и снимает блокировку, как будто вебхук не приходил. Провайдер не получил 200 и повторит вебхук, а повтор обработается нормально. Если повтора не будет (наш фейковый провайдер не ретраит), по дедлайну сработает сторож и переведёт задачу на следующую ногу или сделает возврат. Деньги не теряются и не двоятся. |
| После `COMMIT`, до ответа 200 | Провайдер повторит вебхук, повтор станет no-op: попытка уже не активна, возврат защищён индексом. |
| После `COMMIT`, до отправки следующей ноги (фоновая задача) | Новая попытка уже записана в статусе `pending` с дедлайном. Через `PROVIDER_TIMEOUT` сторож сочтёт её неудачной и поведёт задачу дальше (тест `test_attempt_lost_before_sending_is_recovered_by_watchdog`). |
| Во время `POST /tasks` к провайдеру | Если провайдер всё же принял задачу, его вебхук найдёт попытку по `client_ref` и обработается как обычно, даже если мы не успели сохранить `external_id`. |
| Сторож посреди обработки | Транзакция откатывается, блокировка снимается, на следующем тике задачу заберёт любой живой сторож. |

Компромисс: если процесс упал между коммитом и отправкой, эта нога теряется. Задача не повисает, но вместо повторной отправки на ту же ногу переходит на следующую через `PROVIDER_TIMEOUT`. Повторную отправку `pending`-попыток можно добавить в сторож: повтор безопасен, потому что результат сопоставляется по `client_ref` и второй вебхук той же попытки будет дублем. Но это уже вторая отправка провайдеру, и для тестового я этого не делал.

## Правило 6: поздний completed после того, как сторож сдался

**Решение: результат принимается, пока задача ещё не завершена. Если задача уже завершена, результат записывается в историю и игнорируется.**

- **Сторож перевёл задачу на следующую ногу, задача ещё `processing`.** Поздний `completed` принимается: задача становится `completed` с этим результатом, попытка помечается `late_result=accepted`, активная попытка следующей ноги переходит в `cancelled`. Пользователь заплатил за генерацию, и готовый результат у нас есть, выбрасывать его и ждать следующего провайдера незачем. Если позже придёт результат отменённой ноги, он сохранится в истории с `late_result=ignored`.
- **Сторож исчерпал ноги, задача `failed`, токены возвращены.** Поздний `completed` не меняет задачу: результат сохраняется в истории попытки с `late_result=ignored`, `result_url` задачи остаётся пустым, второй возврат или повторное списание не происходят.
- **Поздний `failed`** ничего не меняет: попытку мы уже сочли неудачной.

Почему задача не может получить и результат, и возврат: оба перехода (`→ completed` с результатом и `→ failed` с возвратом) выполняются только из `processing` и только под одной и той же блокировкой строки задачи. Кто первым взял блокировку, тот и определил исход, второй увидит финальный статус. Гонку `completed` и сторожа на последней ноге проверяет `test_completed_racing_with_watchdog_gives_result_or_refund_never_both`.

Какие варианты я отбросил:
- *Всегда игнорировать поздний результат.* Проще, но мы выбрасываем готовую оплаченную работу и заставляем пользователя ждать следующую ногу, а при последней ноге он получает возврат вместо результата, который уже лежит у нас.
- *Отдать результат после возврата и списать заново.* Это новое движение денег без запроса пользователя: у него может не хватить баланса, и такую операцию сложно объяснить. Деньги должны двигаться только в ответ на явные события.

Цена решения: при принятом позднем результате следующий провайдер мог уже начать работу, и его генерация пропадёт. Это расход на стороне провайдера, деньги пользователя он не затрагивает.

## Настройки

Сервис (env):

| Переменная | По умолчанию | Смысл |
|---|---|---|
| `DATABASE_URL` | `postgresql+asyncpg://postgres:postgres@localhost:5432/generation` | БД |
| `WEBHOOK_SECRET` | `dev-secret` | общий секрет подписи вебхуков |
| `PROVIDER_URLS` | `{"alpha": "http://localhost:9001", "beta": "http://localhost:9002"}` | адреса провайдеров (JSON) |
| `PUBLIC_BASE_URL` | `http://localhost:8000` | база для `callback_url` |
| `PROVIDER_TIMEOUT` | `60` | сколько ждать вебхук, секунд |
| `PROVIDER_HTTP_TIMEOUT` | `5` | таймаут `POST /tasks` |
| `WATCHDOG_ENABLED` / `WATCHDOG_INTERVAL` | `true` / `1` | сторож |
| `MAX_ACTIVE_TASKS` | `3` | лимит активных задач пользователя |

Фейковый провайдер: `FAKE_PROVIDER_NAME`, `FAKE_WEBHOOK_SECRET` и поведение `FAKE_BEHAVIOR__<ПОЛЕ>` (например `FAKE_BEHAVIOR__FAILURE_RATE=0.3`). То же поведение меняется на лету через `PATCH /behavior` и сбрасывается `POST /behavior/reset`.

| Поле | По умолчанию | Смысл |
|---|---|---|
| `min_delay`, `max_delay` | 2, 20 | задержка вебхука, секунд |
| `failure_rate`, `failure_type` | 0, `technical` | доля отказов и их тип (`technical`/`moderation`/`payload`) |
| `sync_error_rate`, `sync_error`, `sync_timeout` | 0, `503`, 30 | синхронный отказ `POST /tasks`: 503 или зависание |
| `duplicate_rate` | 0 | вебхук уходит дважды одновременно |
| `drop_rate` | 0 | вебхук не приходит совсем |
| `late_rate`, `late_delay` | 0, 75 | `completed` приходит через `late_delay`, то есть после `PROVIDER_TIMEOUT` |

## Что сознательно не сделано

- Идемпотентность самого `POST /generate` (заголовок `Idempotency-Key`): в задании её нет, а повтор запроса клиентом создаст вторую задачу с отдельным списанием. Добавляется уникальным ключом на `tasks`.
- Повторная отправка `pending`-попыток после падения процесса (см. выше).
- Ретраи вебхуков на стороне фейковых провайдеров.
- Регистрация, авторизация, хранилище файлов: не нужны по условию.
